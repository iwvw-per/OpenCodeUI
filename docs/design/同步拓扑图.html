A 类 · 服务端权威（消息 / 状态 / 列表 / 权限） B 类 · 账号偏好（主题 / 模型 / 置顶） C 类 · 设备本地派生（未读 / 时间戳 / 排序）

一、物理部署拓扑

opencode 后端跑在每台主机上，前端只是客户端。A 类没有中央同步服务。

二、设备内部逻辑拓扑

一台设备内部同时维持多条连接，全部由 store 与 hook 管理。

三、数据流

A 类 · 服务端权威（每条 server 一条 SSE）

B 类 · 账号偏好（独立账号通道）

C 类 · 设备本地派生（当前各端独立，拟改）

四、多端一致性：哪些一致、哪些不一致

数据通道多端一致原因
消息正文A / SSE一致（同后端）都从后端派生
busy / retryA / SSE理论一致都从后端派生，受目录切分 bug 影响
会话列表A / SSE一致（同后端）sessionListIndexStore
权限 / 提问A / SSE一致activeSessionStore
主题 / 模型 / 置顶B / 账号一致（需登录）preferencesSync
未读 / 已读C / 本地不一致各端独立算（待改为水位同步）
项目时间戳C / 本地不一致各端各自查（待改用服务端时间）
列表排序C / 本地锚点近似锚点本地派生
侧栏开合C / 本地有意不一致属浏览状态

五、延迟来源

合并语义延迟下行为
会话状态replace-scope + seq 缺口检测滞后后收敛
已读水位max 单调递增多显示一会儿未读，永不回退
偏好三方合并 + 时间戳收敛

六、与成熟系统对比

唯一结构性差距是 A 类增量续传：受 opencode 上游限制（不支持从游标重放），只能降级为「缺口检测 + 快照重拉」。其余均可对齐行业最佳实践。
