## 一、结论摘要

问题比预想的大一档，而且**分两个层次**：

| 层次 | 性质 | 规模 |
|---|---|---|
| 样式层 | 同一语义用了不同数值（透明度、颜色、缩放） | hover 背景 **38 种**、hover 文字 **13 种**、焦点环 **16 种**、disabled 透明度 **6 种** |
| 结构层 | 同一个控件在不同文件用不同实现（有的用基础组件，有的手写） | 手写 tab 2 处、手写 switch 2 处、裸 button 仍约 318 处 |

**关键判断**：样式层可以机械收敛，风险低。结构层需要逐个决定"是迁移还是保留"，
其中手写 tab / switch 属于**功能缺陷**（缺键盘导航），不只是样式不一致。

### 3.4 鼠标手型（cursor: pointer）—— 已核实：问题不在 `<button>`

**重要更正**：`<button>` 在浏览器里**默认就是手型**，且本项目用的
Tailwind v4 preflight **没有**把 `cursor` 重置为 `default`
（已核对 `node_modules/tailwindcss/preflight.css`，其中无 button cursor 规则）。

所以 312 处裸 `<button>` 中 292 处虽未写 `cursor-*`，**实际显示仍是手型**，
不需要逐个补。真正缺手型的是**挂在非 `<button>` 元素上的点击**：

| 位置 | 情况 |
|---|---|
| `features/sessions/ProjectSelector.tsx:220` | `<div onClick={onSelect}>` 整行可点，无 `cursor-pointer` → 显示文本光标 |
| `features/chat/sidebar/FolderRecentList.tsx` 等列表行 | 部分行是 `div/span` 承载点击 |

排除项（**不应**加手型，别误改）：

- Dialog / CommandPalette 的遮罩层（`fixed inset-0`）——点击是"关闭"，不该给手型暗示。
- `OutlineIndex.tsx:506` 等 `pointerEvents: 'none'` 的移动感应区。
- `ResizablePanel` 的拖动条——应为 `cursor-row-resize` / `col-resize`（已有）。

**处理方式**：不逐个加类，而是在 `interactive.*` 词汇表里保证各档位自带
`cursor-pointer`（`row` / `subtle` / `danger` / `warning` / `accent` / `card` / `selectedAccent`
都已包含），未纳入词汇表的点击元素再单独补。

## 四、建议的处理顺序

按"收益 / 风险"排序：

### 阶段 A：机械收敛（风险低，可批量）

1. **hover 背景 38 → 6 档**：映射到既有的 `interactive.row / subtle / danger / warning / accent / card`。
2. **hover 文字 13 → 4 档**：`text-100`（主要提升）、`text-200`（次级）、`danger-100`、`accent-main-200`。
   顺带修掉 `hover:text-white` 与 `hover:text-red-400` 两处违规。
3. **disabled 6 档 → 1 档**：统一 `opacity-40` + `cursor-not-allowed`。
4. **焦点环 16 种 → 2 种**：`focusRing`（普通）与 `focusRingCompact`（紧凑）。
   重点修掉 7 处 `border` 焦点环与 2 处无替代的 `outline-none`。

### 阶段 B：激活态统一（方向已定，见第五节）

5. **accent 8 档 → 收敛为中性底**。按用户决定：
   - `selected`（侧边栏会话、文件树、列表行）= `bg-bg-200 text-text-100`
   - accent 浅底仅保留给**标签页 / 筛选 chip** 这类小型强调控件
   - `bg-text-100 text-bg-000` 反色仅保留给小型分段控件（语义确实不同）
   - **统一为 2 档**：`/15`（保留的强调态）与中性底；其余 `/5 /8 /10 /12 /18 /20 /50` 全部收敛

### 阶段 C：结构收敛（风险中，需逐个确认）

6. **手写 tab / switch → 基础组件**（4 处）。这同时是**功能修复**：
   现在键盘用户无法操作这些控件。建议优先做。
7. 裸控件的渐进迁移（按规范"改到该文件时顺带处理"，不做大规模替换）。

## 五、已确定的方案（2026-09-18 用户拍板）

| 项 | 决定 |
|---|---|
| hover 强度基准 | `hover:bg-bg-200`（不透明，明显） |
| 侧边栏会话 / 文件树选中态 | 中性底 `bg-bg-200 text-text-100` |
| 边框 | 由实现方斟酌（见下"边框判断"） |
| 鼠标手型 | 补齐缺失处（见 3.4，重点是非 `<button>` 的点击元素） |

### 边框判断（实现方的结论：hover / 选中态**不加边框**）

结论：**不用边框表达 hover 与选中，一律用底色。** 理由：

1. **边框会改变布局**。`border` 占盒模型空间，未选中态无边框、选中态有边框时
   元素会撑大 2px（或 1px），相邻元素跟着位移。全站列表（侧边栏、文件树、设置项）
   都在可滚动容器里，逐个发生位移会看到轻微抖动。
   若一定要边框，必须写成"未选中态也有透明边框"（`border border-transparent`），
   这是额外的心智负担，且现有代码没有统一这么做。

2. **`ring` 不是替代方案**。Kumo 的"用 ring 代替 border"是为了避免与
   drop shadow 同时出现导致的边缘发虚；但本项目第五节已确认
   `border + shadow` 是既定风格。**hover 态再叠 ring，会与焦点环的 ring 撞车** ——
   键盘用户聚焦时看到 ring，鼠标悬停时也看到 ring，两者无法区分，
   反而破坏"焦点环只在键盘导航时出现"这一约定。

3. **底色已足够表达层级**。本次统一后：
   - hover = `bg-bg-200`
   - 选中 = `bg-bg-200 text-text-100`（**比 hover 多一个文字色提升**）
   - 两者靠**文字色**区分，不靠背景深浅，因此不会出现"hover 和选中看起来一样"的问题。

   > 这是关键设计点：先前 `/40` hover 与 `/12` accent 选中并存时，
   > 两者亮度接近、难以分辨；改用"同底色 + 文字色区分"后层级清晰，
   > 且不需要引入边框。

**唯一保留边框的场景**：需要与周围同色元素明确分隔的**独立卡片/浮层**
（如 `PresetCard`、Toast），它们本就有 `border` 作静态边界，
hover 时**只改边框色或加阴影**，不加新边框。
