# 前端组件与样式约定

最后更新：2026-09-17

本文件约束 `src/` 下的 UI 实现方式，目的是消除同一控件在不同模块各写一遍导致的样式与行为漂移。

## 一、基础组件优先

`src/components/ui/` 是唯一的基础组件来源。写界面时先查这里是否已有可用组件，不要直接手写原生元素。

现有组件：

| 分类 | 组件 |
|---|---|
| 动作 | `Button` `IconButton` `CopyButton` `MenuItem` `ContextMenuItem` |
| 表单 | `Input` `Textarea` `Label` `Checkbox` `Switch` `Select` 系列 |
| 导航 | `Tabs` `TabsList` `TabsTrigger` `TabsContent` `ScrollArea` |
| 浮层 | `Dialog` `DropdownMenu` `Popover` `Tooltip` `ModalShell` |

`Tabs` 有三种视觉变体，按场景选用：

| 变体 | 场景 |
|---|---|
| `segmented`（默认） | 视图切换（如侧边栏主机/项目） |
| `slider` | 设置项等需要滑块位移动画的分段选择 |
| `underline` | 内容区顶部的下划线式导航 |

### 导入方式

```ts
// 推荐：从统一出口导入
import { Button, Input, Tabs, TabsList, TabsTrigger } from '../components/ui'

// 避免：直接引具体文件路径（会绕过 barrel，重构时找不到调用方）
import { Button } from '../components/ui/Button'
```

## 二、样式写法

### 颜色只用设计令牌

```tsx
// 正确
<div className="bg-bg-100 text-text-200 border-border-200" />
<span className="text-accent-main-100" />

// 禁止
<div className="bg-white text-black" />
<div style={{ color: '#fff' }} />
```

可用令牌见 `src/index.css` 的 `@theme` 块。7 套主题 × 明暗模式都会覆盖这些变量，硬编码颜色无法跟随主题切换。

### 强调色的正确用法

激活/选中态用**浅底 + 主文字色**，不要用高饱和实色铺满：

```tsx
// 正确：全主题下对比度 >= 9.9:1
'bg-accent-main-100/15 text-text-100'

// 禁止：白字对 accent 底对比度最低仅 2.1:1，且视觉过重
'bg-accent-main-100 text-white'
```

需要实色强调背景时，文字必须用 `text-oncolor-100`（主题感知的对比色），而不是硬编码 `text-white`。

### 交互态用统一的词汇表

hover / active / focus 的写法**不要手写**，从 `src/utils/interaction.ts` 引用：

```ts
import { interactive } from '../../utils/interaction'

// 列表行 / 菜单项
<button className={cn(interactive.row, 'px-2 h-8')} />

// 密集排布的图标按钮、折叠标题栏
<div className={cn(interactive.subtle, 'px-2 py-1')} />

// 删除 / 断开（配 hover:text-danger-100）
<button className={cn(interactive.danger, 'p-1 rounded-md')} />
```

| 语义 | 用途 | hover 底色 |
|---|---|---|
| `interactive.row` | 列表行、菜单项、下拉选项 | `bg-bg-200` |
| `interactive.rowSelected` | 列表行选中态 | `bg-bg-200 text-text-100` |
| `interactive.subtle` | 密集图标按钮、折叠标题栏 | `bg-bg-200` |
| `interactive.danger` | 删除、断开、清空 | `bg-danger-100/10` |
| `interactive.warning` | 重置、还原（可恢复但有损失） | `bg-warning-100/10` |
| `interactive.accent` | 打开、跳转、新增 | `bg-accent-main-100/10` |
| `interactive.card` | 整块可点击但内部还有控件 | `bg-bg-200` |
| `interactive.focusRing` / `focusRingCompact` | 键盘焦点环 | — |
| `interactive.disabled` | 禁用态 | — |
| `selectedAccent` | 强调式选中（标签、筛选 chip） | `bg-accent-main-100/15` |

理由：此前同一个「列表项悬停」在全站出现了 `bg-bg-200`、`/50`、`/60`、`/40`、`/30`
等 20 余种写法，差异没有设计依据，改一处也影响不到其他处。收敛成语义档位后，
调整全站交互观感只需改 `interaction.ts` 一个文件。

#### 硬性约定一：hover 与选中态不用边框，也不用 ring

- hover = `bg-bg-200`，选中 = `bg-bg-200 text-text-100`：**同底色，靠文字色区分层级**。
- **不要加边框**：`border` 占盒模型空间，未选中无边框、选中加边框会让元素撑大
  1~2px 并推动相邻元素（列表在滚动容器里表现为抖动）。若确需边框，必须两态都写
  （未选中为 `border-transparent`），本项目不采用这种做法。
- **不要用 `hover:ring-*`**：`ring` 在本项目里是**键盘焦点**的专用表达
  （`focus-visible:ring-*`）。hover 也用 ring，鼠标悬停与键盘聚焦将无法区分，
  「焦点环只在键盘导航时出现」这条约定即失效。

  例外：面板/分屏的**焦点指示**（如 `ChatPane` 的 `isFocused` 高亮）语义上确实是
  「哪个面板处于活动焦点」，用 ring 恰当，不属此列。

#### 硬性约定二：按下反馈不得改变几何

禁止 `active:scale-*` / `active:translate-*` / `active:rotate-*` / `active:skew-*`。

缩放与位移会让元素在按下瞬间改变视觉边界，在密集列表里看起来像相邻元素在抖动，
也违背「点击不改变布局」的工程稳定性要求。按下反馈**只用颜色/透明度**：

```
hover:bg-bg-200  →  active:bg-bg-300
```

回归测试：`src/components/ui/actions.test.tsx` 的「never changes geometry on press」。

#### 鼠标手型

`<button>` 在浏览器里默认即为手型，**不需要逐个补 `cursor-pointer`**
（Tailwind v4 preflight 未重置 button 的 cursor）。

真正需要补的是**挂在非 `<button>` 元素上的点击**，例如 `ProjectSelector.tsx` 里
`<div onClick={onSelect}>` 的整行。词汇表各档位已内置 `cursor-pointer`，
覆盖不到的点击元素再单独补。

**不要**给这些加手型（它们不该有「可点」暗示）：Dialog / CommandPalette 的遮罩层、
`pointerEvents: 'none'` 的感应区、拖动条（应为 `cursor-row-resize` 等）。

**例外（保留手写）**：拖动分隔条（resize handle）的 `hover:bg-accent-main-100/50
active:bg-accent-main-100` 是有意的可拖动提示，与 `isResizing` 状态联动，不适用本表。

#### 底色令牌有两条阶梯，按"元素坐在哪一层"选

主题里有两条相邻色阶，hover 该取哪一档取决于元素所处的**容器底色**：

| 元素所处容器 | hover 取 | 例子 |
|---|---|---|
| `bg-100`（面板、侧边栏、设置分组） | `bg-200` | 列表行、图标按钮 |
| `bg-000` / `bg-050`（最底层页面、透明输入框） | `bg-100` | `fieldClass` 上叠加的清除/下拉按钮 |

也就是说 `hover:bg-bg-100` **不一定是漂移** —— 它出现在透明底
（`bg-transparent`，如 `fieldClass`）或直接坐在 `bg-000` 的元素上时是正确的，
硬改成 `bg-200` 会明显偏暗。

**判定方法**：往上看最近一个**静态**底色容器（不是另一个 hover）。
若它是 `bg-100`/`bg-200`，hover 取上一档；若是 `bg-000`/透明，取 `bg-100`。

**真正的漂移**是同一容器内、同类元素用了不同档位。典型例子：
`ProjectSelector.tsx` 里两个功能相同的整行可点项目行，一个写 `hover:bg-bg-200`、
另一个写 `hover:bg-bg-100` —— 这种要统一到该容器的正确档位。

#### 选中态：先判断是「行」还是「小控件」

选中态不要各自调透明度。按元素面积与语义选两档之一：

| 场景 | 用法 | 取值 |
|---|---|---|
| 列表行、文件树、会话项（大面积） | `interactive.rowSelected` | `bg-bg-200 text-text-100` |
| 标签页、筛选 chip、设置项（小面积强调） | `selectedAccent` | `bg-accent-main-100/15 text-text-100` |

判定依据：
- **大面积用中性底**。accent 浅底铺在大色块上会压过内容，且与 hover 形成两种色相。
- **小面积用 accent 底**。元素小时 accent 能提供明确的"当前项"识别。
- 两者都与 hover 同强度或略强，靠**文字色**（`text-text-100`）拉开层级。

**菜单的键盘高亮项等同于 hover**：`CommandPalette` / `MentionMenu` /
`SlashCommandMenu` 里被方向键选中的项，语义是"当前落在哪一项"，应与鼠标 hover
用同一个底色（`bg-bg-200`）。此前这些用 accent 浅底，而鼠标 hover 用 `bg-bg-200`，
同一个"当前项"出现两种视觉，现已统一。

**`bg-accent-main-100/N` 的其余合法用途**（不要误改）：
- `/50` 用于拖动分隔条的可拖拽提示。
- `/5` + `ring-accent-main-100/20` 用于"正在编辑/捕获输入"这类带边框的强调态。
- 图标底衬、胶囊按钮、拖放高亮等装饰性使用。

### 圆角按层级选用固定刻度

刻度定义在 `src/index.css` 的 `@theme` 块，取值与 Tailwind 默认值一致（也与 Cloudflare Kumo 设计系统的 `--radius-*` 一致）。按元素在视觉层级中的位置选用：

| 层级 | 类 | 值 | 典型元素 |
|---|---|---|---|
| 小标记 | `rounded-xs` | 2px | 徽标、内联标签 |
| 控件 | `rounded-sm` | 4px | 紧凑控件、分段控件外层 |
| 控件 | `rounded-md` | 6px | 按钮、输入框、菜单项、下拉选项 |
| 容器 | `rounded-lg` | 8px | 卡片、列表项、面板 |
| 浮层 | `rounded-xl` | 12px | Dialog、DropdownMenu、Select、Popover、浮动面板 |
| 大容器 | `rounded-2xl` | 16px | 消息气泡、输入区 |
| 圆形 | `rounded-full` | — | 头像、开关、状态点 |

核心原则：**层级越"浮"，圆角越大**，同时**紧凑控件配更小的圆角**。

不要使用任意值（`rounded-[14px]` 这类魔法数字）。刻度之外的取值会破坏层级梯度，也会让子元素的继承值无处可循。

> 历史提示：这套刻度曾被整体上移一档（`sm`/`md` +2px、`lg`/`xl`/`2xl` +4px），导致小尺寸元素圆角占高度比例过高（`h-8` 列表项达 37.5%、`size-6` 图标按钮达 33%），观感偏浮。现已恢复默认刻度。若将来调整，请只改 `index.css` 的 `@theme`，不要逐个改组件。

### 紧凑控件需要收一档

同样的圆角值，控件越矮占比越大，视觉上越"圆"。侧边栏的同类元素是 `h-8`（32px）配 8px（占 25%），而分段切换器整体只有约 25px 高，沿用 8px 会占 32%，明显偏圆。

因此 `Tabs` 的 `size` 同时决定圆角：

| size | 高度 | 容器 | 内层 |
|---|---|---|---|
| `sm`（默认） | ~25px | `rounded-sm` (4px) | `rounded-xs` (2px) |
| `md` | ~32px | `rounded-lg` (8px) | `rounded-md` (6px) |

判断依据不是"某个值好不好看"，而是**圆角占控件高度的比例**是否与同类元素接近。

`size` 与 `variant` 只需在 `<Tabs>` 上传一次，`TabsList` / `TabsTrigger` 会通过 context 自动继承：

```tsx
// 正确：根节点声明一次
<Tabs variant="slider" size="md" value={v} onValueChange={setV}>
  <TabsList activeIndex={i} itemCount={n}>
    <TabsTrigger value="a">A</TabsTrigger>
  </TabsList>
</Tabs>
```

此前需要在三处各自传 `size`/`variant`，漏传会导致内外层圆角不匹配（外层取默认 sm、内层显式 md，内层圆角反而大于外层，弧线肉眼可见地对不上）。

### 嵌套圆角必须同心

来自 Kumo 设计系统的规则：当边框或 ring 之间的距离 ≤ 8px 时，内层圆角必须与外层**数学上同心**。

```
外层半径 = 内层半径 + 中间的内边距
```

多数情况下内层直接填满外层（无内边距），因此：

```tsx
// 正确：内层无内边距，与外层同值
<div className="rounded-xl overflow-hidden">
  <div className="rounded-t-xl bg-bg-000">…</div>
</div>

// 禁止：内层值不匹配，边角会出现错位
<div className="rounded-[14px] overflow-hidden">
  <div className="rounded-t-[14px] bg-bg-000">…</div>
</div>
```

若外层容器有内边距（如 `p-1`），内层应取 `外层值 - 内边距`。

### 组件必须 `type="button"`

原生 `<button>` 在表单内默认 `type="submit"`。基础组件统一声明 `type = 'button'`，
调用方可显式传 `type="submit"` 覆盖：

```tsx
<button type={type} … />   // type 默认 'button'
```

写裸 `<button>` 时务必显式写 `type="button"`，否则放进 `<form>` 会意外提交。

### 用 cn 合并类名

组件接受 `className` 时，用 `cn()` 合并，让调用方传入的类能正确覆盖默认值：

```tsx
import { cn } from '../../utils/cn'

className={cn('px-2.5 text-[length:var(--fs-sm)]', sizeStyles[size], className)}
```

`cn` 内部用 tailwind-merge 消解同类冲突（`px-5` 会覆盖 `px-2.5`），手写字符串拼接做不到这点。

## 三、组件编写约定

### 结构

```tsx
import { forwardRef } from 'react'
import { cn } from '../../utils/cn'

export interface FooProps extends React.HTMLAttributes<HTMLDivElement> {
  variant?: 'a' | 'b'
}

export const Foo = forwardRef<HTMLDivElement, FooProps>(({ className, variant = 'a', ...props }, ref) => (
  <div ref={ref} className={cn(baseStyles, variantStyles[variant], className)} {...props} />
))
Foo.displayName = 'Foo'
```

要点：

- `forwardRef` 转发 ref，让调用方能拿到 DOM 节点（聚焦、定位、测量都需要）。
- 变体样式抽成 `Record<Variant, string>` 常量，不要写成嵌套三元表达式。
- 必须设 `displayName`，否则 React DevTools 里显示为匿名组件。
- 透传 `...props`，不要吞掉调用方的原生属性。

### 复杂交互用 Radix 原语

涉及键盘导航、焦点管理、ARIA、碰撞避让的组件（Tabs / Select / Popover / Tooltip / Checkbox / Switch / Dialog），基于 `@radix-ui/react-*` 实现。Radix 只提供行为与无障碍支持，不带任何样式，视觉仍由本项目的设计令牌控制。

不要自己手写这些逻辑 —— 焦点陷阱、roving tabindex、ESC 关闭这些细节极易出错。

### 什么时候该抽组件

同一控件在**两处以上**出现，或单个文件里同种原生元素超过 5 个时，应当抽成基础组件。判断标准不是"能不能抽"，而是"下次别人写这个控件时会不会又写一遍"。

## 四、测试约定

基础组件测试放在 `src/components/ui/` 下，与组件同目录。

- 用 `@testing-library/react` 的 `fireEvent`（项目未引入 `user-event`）。
- 断言语义与结构（role、aria 属性、data-state），不断言具体类名 —— 除非是回归保护（如防止激活态退回 `text-white`）。
- 不测第三方原语的行为（Radix 自身保证），只测自己写的样式映射与结构契约。

注意两个 Radix 在 jsdom 下的行为：

- `TabsTrigger` 在 `mouseDown` 上激活，不是在 `click` 上。测试需 `fireEvent.mouseDown` 并包在 `act` 里。
- 非激活的 `TabsContent` 节点仍在 DOM，但不带 `role="tabpanel"` 且内容为空。

## 五、待办：渐进式收敛

现有代码中存在大量手写控件（当前约 318 处裸 `<button>`、92 处裸 `<input>`）。迁移策略是**渐进**的：

1. 新代码一律使用基础组件。
2. 修改老文件时，顺手把该文件内的手写控件换成基础组件。
3. 不做专门的大规模替换 —— 那类改动风险高且难以验证。

**例外**：`hover:bg-accent-main-100/10` 这类纯样式重复不属于"手写控件"，
它们已通过 `interactive.accent` 收敛（见第二节），可以批量处理，因为改动是
逐字面等价的，不涉及结构。

已完成的高价值迁移：

- `SettingsUI.tsx` 的 `SegmentedControl` → 内部改用 `Tabs` 的 slider 变体（原先手写键盘处理，且缺 ARIA 关联）。

## 六、待议：border 与 drop shadow 共用

Kumo 设计系统有一条规则：不要同时使用 `border` 与 drop shadow，改用 `ring` 表达边界以保持边缘锐利。

本项目当前有 20 余处容器同时使用两者（`Dialog`、`DropdownMenu`、`Select`、`Popover`、`ToastContainer`、`CommandPalette` 等），已形成既定风格且视觉自洽。全站改到 `ring` 方案属于大范围视觉变更，需要逐一确认效果，因此暂不执行。

新代码沿用现状（`border` + `shadow-lg`）；若要统一改造，应作为独立的设计调整批次处理，而不是零散修改。
